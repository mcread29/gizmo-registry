Git can push now — `f2a2599`.

**Server** (`packages/git/src/server`):
- `GitService.push(projectPath, { setUpstream })` — runs `git push`, or `git push --set-upstream origin <branch>` when asked to publish. Returns the branch, whether it published, and git's own report (git writes progress to stderr). No force-push path.
- `GitService.pushState(projectPath)` — branch, upstream, ahead/behind counts (via `rev-list --left-right --count HEAD...@{upstream}`), and `hasCommits` for empty repos.
- Two new operations on the descriptor: `push-state` (read-only) and `push` (mutating, `requiresConfirmation: true`). Both callers pass `confirmed: true` — clicking the control is the confirmation. Capabilities now list `push`.

**One design constraint worth knowing:** I deliberately did *not* add `upstream`/`ahead`/`behind` to `GitStatus`. The app parses that payload with its own `@gizmo/protocol` schema (`additionalProperties: false`), which lives in the Gizmo repo, not here — extra fields would have thrown in `GitCapability` and broken the panel. Hence a separate operation.

**UI** (`ChangesPanel.svelte`): a Push button next to "Commit all" in the header row. It reads **Publish** when the branch has no upstream, shows the ahead count (`Push 2`), and is disabled while pushing, when push state is unknown, in a repo with no commits, or when the branch is already up to date. Push state reloads after a commit and after each push. Command palette gained **Push commits** (`Upload` icon, keywords push/publish/remote).

**Not added:** an agent-facing `git_push` tool. The extension only exposes `git_status` to the model today, and given your guardrail work on blocking destructive git commands, pushing felt like something to keep human-initiated. Say the word if you want the tool.
