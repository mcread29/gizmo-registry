## What's actually safe

A session that's already running holds the module graph it imported at startup. Gizmo's own code notes this: after a registry update it rescans, but "Node's ESM cache serves the module graph it already loaded for an unchanged path, so an extension that was linked before this update keeps running its old code until the server restarts." So a running thread won't swap code under itself — but it *will* pick up your edit on `/reload`, `/new`, `/resume`, or `/fork`.

## Real hazards

1. **Mid-edit startup.** A thread that starts while a file is half-written imports broken TS and fails tool registration. Keep edits atomic; write whole files.
2. **The build writes in place.** `scripts/build-web-extension.ts` finishes with a single `writeFile(target, ...)` — no temp-and-rename. Brief window where the bundle is truncated, and anything loading it fails. Also: web changes do nothing until you run `pnpm build`.
3. **Shared packages have wide blast radius.** `packages/unity`, `packages/git`, `packages/activity`, `packages/ui`, `packages/protocol` are imported by several extensions at once.
4. **Tool schema/name edits.** Sessions that already advertised a tool to the model can hit provider errors after the schema shifts; old tool calls in a resumed thread may not resolve.
5. **Bundle over 8 MB** is dropped with only a diagnostic — the extension's UI silently vanishes for everyone.
6. **Lockfile drift.** `gizmo.registry.json` builds with `pnpm install --frozen-lockfile && pnpm build`. Add a dependency without updating `pnpm-lock.yaml` and the app-side build breaks for every user.
7. **Git state vs. the app.** `registryUpdate` runs `git pull --ff-only`. You're currently `main...origin/main [ahead 3]` (HEAD `6ad00e6`, installed commit `fa038ec`) — unpushed commits or a dirty tree can make that pull fail, and any checkout/reset would discard uncommitted work.
